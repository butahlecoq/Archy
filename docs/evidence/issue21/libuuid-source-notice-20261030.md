# Issue #21: historical libuuid source and notice evidence

The independently reviewed historical [54-file inventory](arch-system-files-54.json) identifies `/usr/lib/libuuid.so.1.3.0` as owned by `util-linux-libs 2.42.4-1`, SHA-256 `7881e0279d5ce79b0d8ace923e94df9b543bc8dd8152df0894358b862e1725be`. The archived [Arch split package](https://archive.archlinux.org/packages/u/util-linux-libs/util-linux-libs-2.42.4-1-x86_64.pkg.tar.zst) has SHA-256 `56075bc7da9be4470da36a040195f98aac0afbc1edcc7e4f27e6d267dcaf9f37`; its `.PKGINFO` says `util-linux-libs 2.42.4-1` with `pkgbase = util-linux`, and its `libuuid` bytes have that exact inventory hash. Its detached [package signature](https://archive.archlinux.org/packages/u/util-linux-libs/util-linux-libs-2.42.4-1-x86_64.pkg.tar.zst.sig), SHA-256 `bddb21c95e98285c7c424415e9995270f595bcf47b80689b1045d8ff81d4b3c9`, verified with signing subkey fingerprint `0429897DE5F3BDAC537A30696D42BDD116E0068F` under Christian Hesse's primary key `02FD1C7A934E614545849F19A6234074498E9CEE`.

The exact [Arch recipe tag](https://gitlab.archlinux.org/archlinux/packaging/packages/util-linux/-/tree/2.42.4-1) peels to commit `1959b6ecef6b57acd92ca97b783553174b747f6a`; the [saved PKGBUILD](../../../packaging/arch/issue21-source-notices/util-linux-libs/PKGBUILD) has SHA-256 `bf6f0382d3ed8ab51c36b8cfcc8af238e60bd8a3cd7a6d4109dc4ba55b23b18c`. It declares `pkgname=(util-linux util-linux-libs)`, pins signed upstream Git tag [`v2.42.4`](https://github.com/util-linux/util-linux/releases/tag/v2.42.4), and moves `lib*.so*` into `util-linux-libs`. The upstream tag is an annotated signed object `a1d2b6980b84f38b389a6d6dda4a9623f47d13be`, peeling to commit `d76cbf8f13e65ff657344f7f6a90042cf755ba59` and tree `2b1bca56bae90356243e14c80b947fc625d9a897`. Its signature verified under the recipe's allowed fingerprint `B0C64D14301CC6EFAEDF60E4E4B71D5EEC39C284` (Karel Zak). The source `meson.build` sets `libuuid_version = '1.3.0'`, matching the binary filename; this is a naming check, not a build reproduction.

The upstream [`libuuid/COPYING`](../../../packaging/arch/issue21-source-notices/util-linux-libs/libuuid-COPYING), SHA-256 `5068749ee9c2f2c545af4a4de9fde3c39dc8d90af47cc0b3a42700116f9b7e71`, points to its full BSD-3-Clause text. All five full license files shipped in the signed package are saved in the [util-linux-libs notice directory](../../../packaging/arch/issue21-source-notices/util-linux-libs/): `COPYING.BSD-2-Clause` (`527f738966ca396cd5a68c1509390de2a780c6b614d9ee57f7544a6161938ed1`), `COPYING.BSD-3-Clause` (`9b718a9460fed5952466421235bc79eb49d4e9eacc920d7a9dd6285ab8fd6c6d`), `COPYING.BSD-4-Clause-UC` (`ba7640f00d93e72e92b94b9d71f25ec53bac2f1682f5c4adcccb0018359f60f8`), `COPYING.ISC` (`e53348ce276358e9997014071c5294b36a18c4b34f32f00ee57b9acce0aafd63`), and `util-linux-BSD-2-Clause.txt` (`6ffedbc0f7878612d2b23589f1ff2ab15633e1df7963a5d9fc750ec5500c7e7a`). The first four match files in the signed upstream tree; the final file matches the PKGBUILD's pinned checksum for its extra xxHash license input. The package's SPDX labels also include GPL and LGPL variants and public domain, reflecting the broader split package rather than a determination for this library. `libuuid` compiles shared `randutils`, MD5 and SHA-1 code; source-file header notices need a separate legal mapping before distribution.

Signature verification used keys fetched by fingerprint into private scratch; key certification against an independent trust root was not established. The source tag, recipe, signed package, and exact ELF hash form a historical correspondence chain, but no reproducible source-to-binary build was run. This does not identify a current Omarchy target package or grant distribution or legal approval.

## Source header mapping at the verified v2.42.4 tree

The [Meson libuuid target](https://github.com/util-linux/util-linux/blob/v2.42.4/libuuid/meson.build) explicitly supplies 11 `libuuid/src/*.c` files and three shared `lib/*.c` files. `pack.c` appears in `lib_uuid_sources` and is also assigned to `pack_c` for a separate test; it is counted once in the library. The target also names `include/list.h` through `list_h`. The 11 library-local C files are `clear`, `compare`, `copy`, `gen_uuid`, `isnull`, `pack`, `parse`, `predefined`, `unpack`, `unparse`, and `uuid_time`. The shared C files are `randutils`, `md5`, and `sha1`. These are build-definition inputs, not an observed compiler command or source-to-binary reproduction.

The [26-row source inventory](../../../packaging/arch/issue21-source-notices/util-linux-libs/libuuid-source-notices.tsv) records each C file and relevant project header, its SHA-256 from the exact Git commit, and its leading notice. The [checker](../../../scripts/issue21/verify_libuuid_source_notices.py) checks the tag object, commit, tree, Meson source list and shared-source variables, quoted-include header closure, file hashes, notice classes, and the saved LGPL text. `include/list.h` is a Meson input but is not in that quoted-include closure; the inventory does not assert that it contributes code to the shared object. The closure includes `include/timeutils.h` through `gen_uuid.c` and `uuid_time.c`, though these C files do not call the inline functions named in that header. This distinction matters when assessing the binary and its obligations.

## `list.h` provenance and build relevance follow-up

At the verified util-linux tag, [`include/list.h`](https://github.com/util-linux/util-linux/blob/v2.42.4/include/list.h) is blob `b6bbbdd8fef7020ffea3ca77b0c4e194d460ac6a`, SHA-256 `8bce25453bd2710e735facdf7f0313114e57eb93b27d392d89960a3d8c867c64`. Its leading notice names Karel Zak and Theodore Ts'o and says “GNU Lesser General Public License” without a version, “or later,” SPDX identifier, or exception. The [2013 copyright cleanup](https://github.com/util-linux/util-linux/commit/0f23ee0c855d686b0c315af2c96b8835134cd9e3) (`0f23ee0c855d686b0c315af2c96b8835134cd9e3`) added that wording to the header. Its commit message says LGPL was used for code copied from libraries; it gives no version. A full-history `git log v2.42.4 --follow -G 'License|license|exception|SPDX' -- include/list.h` found that as the only license-wording change along this path through v2.42.4. The [release's `README.licensing`](https://github.com/util-linux/util-linux/blob/v2.42.4/README.licensing), SHA-256 `4c2db318192bda62f3f8fcf71488bb5e602ae4385eba281d711b46cc13a40bb3`, lists LGPL-2.1-or-later among project licenses and directs readers to file headers. It does not assign that version specifically to `list.h`. The saved LGPL text likewise cannot supply a version missing from this header by itself.

The [2008 util-linux import](https://github.com/util-linux/util-linux/commit/a0948ffe403658f567a9267f50a26a694fe417da) (`a0948ffe403658f567a9267f50a26a694fe417da`) added `libs/blkid/src/list.h` while merging code from e2fsprogs `lib/blkid`. Its SHA-256 `9c8b54608e793a368b19981c69265884351ddba5c1f9b235284787c6ff0bd51f` matches [e2fsprogs v1.41.0 `lib/blkid/list.h`](https://github.com/tytso/e2fsprogs/blob/v1.41.0/lib/blkid/list.h) byte for byte (tag commit `92e49d85b4528362d349ef8df082b695f6ecbea4`). Neither file has a license/version/exception line. The [2010 move](https://github.com/util-linux/util-linux/commit/c391642d0f4e554fbc3e256dff90fa771612e517) (`c391642d0f4e554fbc3e256dff90fa771612e517`) created `include/list.h` from the libmount list implementation, itself labeled “based on list.h from e2fsprogs”; subsequent code changes mean the current file is not byte-identical to the imported e2fsprogs file. The [e2fsprogs v1.41.0 `COPYING`](https://github.com/tytso/e2fsprogs/blob/v1.41.0/COPYING) names exceptions for several libraries, including a BSD-style lib/uuid exception, but does not name `lib/blkid` or `list.h`. These historical facts do not settle how the util-linux header's later LGPL wording should be interpreted.

Build evidence has three levels. First, the exact [`libuuid/meson.build`](https://github.com/util-linux/util-linux/blob/v2.42.4/libuuid/meson.build), SHA-256 `0119426fd9f5a1b391e02884b1e510e7de4ef16282adee7a145a7951c69d8ef4`, passes `list_h` to `library('uuid', ...)`, and [`include/meson.build`](https://github.com/util-linux/util-linux/blob/v2.42.4/include/meson.build) defines it as `files('list.h')`. This establishes a build-definition input, not compilation of the header. Second, the existing source checker finds no `list.h` in the 14 C inputs' project-local quoted-include closure. A separate [compiler dependency probe](../../../scripts/issue21/check_libuuid_list_dependency.py) ran `cc -MM` on those 14 inputs from a clean checkout of commit `d76cbf8f13e65ff657344f7f6a90042cf755ba59`; all passed without `include/list.h` among their reported dependencies. That probe uses local Linux headers and a synthetic `HAVE_NANOSLEEP` definition to get through `include/c.h`, so it is not an observation of Arch's configured compile commands. It excludes the test target and linked dependencies. Third, the signed Arch package contains the inventory-matching `libuuid.so.1.3.0` SHA-256 `7881e0279d5ce79b0d8ace923e94df9b543bc8dd8152df0894358b862e1725be`, but no source-to-binary reproduction or archived compiler dependency trace has been established. The source evidence strongly suggests `list.h` does not contribute to that library's compilation under the checked Linux configuration; it does not establish that claim for the exact archived build or infer any notice obligation from the binary.

Reproduce the local compiler probe with `python3 scripts/issue21/check_libuuid_list_dependency.py /path/to/clean/util-linux-v2.42.4-checkout`. It requires a C compiler and the exact tag commit as `HEAD`; it prints one dependency result per C input. No Meson/Ninja or system package installation is needed. The unresolved items remain an authoritative explicit version or exception for this specific header, if one exists outside the inspected history, and actual configured build/compiler evidence for the archived ELF. No legal or distribution decision follows from this note.

### Independent reproduction

Use a disk-backed checkout of the [upstream v2.42.4 tag](https://github.com/util-linux/util-linux/releases/tag/v2.42.4), then run from this Archy worktree:

```sh
git -C /path/to/util-linux rev-parse v2.42.4 v2.42.4^{commit} v2.42.4^{tree}
# Expected, in order: a1d2b6980b84f38b389a6d6dda4a9623f47d13be
# d76cbf8f13e65ff657344f7f6a90042cf755ba59
# 2b1bca56bae90356243e14c80b947fc625d9a897
git -C /path/to/util-linux tag -v v2.42.4
python3 scripts/issue21/verify_libuuid_source_notices.py /path/to/util-linux
sha256sum packaging/arch/issue21-source-notices/util-linux-libs/{PKGBUILD,COPYING.LGPL-2.1-or-later,libuuid-source-notices.tsv}
```

The checker compares bytes from Git objects, so the checkout worktree can remain detached and clean. `git tag -v` needs the upstream signing key; its output must be evaluated with the key-certification caveat above. The checker does not independently establish signature trust.
