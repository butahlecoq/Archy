# Issue #21: libXt transitive library inventory

Base: `a601e4d1c92c9c9859b4059ae8737a745581efa4`. This is a read-only source and archive audit in a new worktree with private disk scratch. It adds no library, package, runtime allowlist, review record, or target approval. Independent review of this evidence is pending.

## Pinned payload and requesters

The official Blender 4.5.15 Linux x64 archive downloaded from `https://download.blender.org/release/Blender4.5/blender-4.5.15-linux-x64.tar.xz` matched the already pinned SHA-256 `0d2b8bb2efe97e6c8eb57de6b7322f8800e1984e3125b60decca5f6771e4773e`. Its 6,510 tar members have **no member named** `libXt.so*`, `libSM.so*`, `libICE.so*`, `libX11.so*`, `libxcb.so*`, `libXau.so*`, `libXdmcp.so*`, or `libuuid.so*`. The runtime stager copies the Blender archive under `/usr/lib/archy/runtime/blender`; that extraction step does not add any of these libraries. The runtime recipe instead declares the system package owners `libice`, `libsm`, `libx11`, `libxcb`, `libxau`, `libxdmcp`, and `util-linux-libs` among its dependencies. Thus none of the three requested SONAMEs is supplied **by the pinned Blender payload**; all three are expected from `/usr/lib` on the build/target system. A package dependency declaration does not establish the exact target bytes.

All 212 regular ELF files in the archive were examined with `readelf -dW`; symlink aliases were excluded because they point to the same regular ELF bytes. [The path-level result](../evidence/issue21/blender-x11-requesters.json) records the 44 files with a direct need for at least one of these libraries; its SHA-256 is `95d54d272654ced66f342095c2ff777d8df79c508c3232a4463f7b9fdb8ae070`. Counts of direct requesters are `libSM.so.6`: 41; `libICE.so.6`: 41; `libX11.so.6`: 43; `libXt.so.6`: 3; `libuuid.so.1`: 1. The three `libXt` requesters are MaterialX's `PyMaterialXRenderGlsl`, `libMaterialXRenderGlsl.so.1.39.2`, and `libMaterialXRenderHw.so.1.39.2`. Both native MaterialX render libraries and that Python extension also directly request all three libraries in this audit. The Blender executable directly requests `libX11.so.6`; 38 USD-related binaries and the bundled Mesa GL library contribute other direct requests. The JSON gives exact paths rather than relying on those group descriptions. No bundled ELF directly requests `libxcb.so.1`, `libXau.so.6`, or `libXdmcp.so.6` in this scan.

The existing host-built libXt source candidate, SHA-256 `e219ba432d1bc372860ad04b090b75be63efe60c0e5a8d53ee949b937b1d6ab8`, was re-read with `readelf`: its SONAME is `libXt.so.6`; direct needs are exactly `libSM.so.6`, `libICE.so.6`, `libX11.so.6`, and `libc.so.6`, without RPATH or RUNPATH. This is the already documented Ubuntu feasibility binary, not a new build or a proposed payload.

The earlier runtime handoff reports 54 hash-pinned `/usr/lib` system files in a disposable Arch build-image inventory. That generated inventory and its exact 54 rows are not checked in at this PR head, and the final source manifest still has pending A12/distribution reviews. This pass verifies the archive and recipe classification, **not** those historical system file hashes or availability on Omarchy. The runtime also stages CPython and 15 IFC wheels; this audit did not reconstruct their full packaged file inventory. An eventual candidate inventory must be checked for duplicate SONAME providers and for the exact resolved paths and hashes.

## Next ELF edges and source/notice gaps

An independent `readelf -dW` pass on this Ubuntu host gives the following conditional graph: `libSM.so.6` needs `libICE.so.6`, `libuuid.so.1`, and `libc.so.6`; `libICE.so.6` needs `libc.so.6`; `libX11.so.6` needs `libxcb.so.1` and `libc.so.6`; `libxcb.so.1` needs `libXau.so.6`, `libXdmcp.so.6`, and `libc.so.6`; `libXau.so.6` and `libXdmcp.so.6` need `libc.so.6`; `libuuid.so.1` needs `libc.so.6` and the ELF loader. This graph is **not** a verified Arch or target ELF graph. Current Arch package metadata independently lists [libsm](https://archlinux.org/packages/extra/x86_64/libsm/) depending on libice and util-linux-libs, [libx11](https://archlinux.org/packages/extra/x86_64/libx11/) on libxcb, and [libxcb](https://archlinux.org/packages/extra/x86_64/libxcb/) on libxau and libxdmcp. [libice](https://archlinux.org/packages/extra/x86_64/libice/), [libxau](https://archlinux.org/packages/extra/x86_64/libxau/), [libxdmcp](https://archlinux.org/packages/extra/x86_64/libxdmcp/), and [util-linux-libs](https://archlinux.org/packages/core/x86_64/util-linux-libs/) complete the package-owner leads. These live pages are leads, not immutable source or binary pins.

Before treating this path as a distributable runtime closure, recover the exact system-file rows and owning package versions from the pinned build-image inventory, then inspect those exact Arch ELF bytes for SONAMEs, direct needs, symbol-version requirements, and resolved `/usr/lib` paths. Pin each corresponding upstream source archive/revision and Arch recipe/signature evidence; establish source-to-binary correspondence or record its limit. Collect and hash applicable full license/notice texts for libSM, libICE, libX11, libxcb, libXau, libXdmcp, util-linux's libuuid, and the linked glibc/runtime components. Review the source/build dependency set separately (`xorgproto`, `xcb-proto`, `xtrans`, and build tools); package metadata alone does not supply source or notice evidence. `packaging/arch/runtime-notices/` currently has no notice texts for those seven libraries. Recheck closure and notices after any payload or build-image change.

The current recipe already names the relevant runtime package owners, so adding duplicate dependency declarations would provide no evidence. This pass records the verified archive requesters and the unresolved exact-binary/source/notice requirements. It does not repeat the libXt, libxcrypt, or IfcOpenShell source builds, install host packages, alter service policy, open trust gates, or claim distribution or target acceptance.
