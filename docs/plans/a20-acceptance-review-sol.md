## Concrete issues to correct in the matrix

1. **Broken evidence link.** The “GitHub Actions retention is finite” link in the published-head checkpoint returns HTTP **404**: `https://docs.github.com/en/organizations/managing-organization-settings/configuring-the-retention-period-for-checks-workflow-runs-commit-statuses-artifacts-and-logs-in-your-organization`. The supported claim is sound, but cite the live [GitHub repository Actions settings documentation](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), which describes the retention policy. The other 17 distinct external URLs returned HTTP 200 in this check; all 39 relative links resolve to existing files locally. HTTP 200 verifies reachability, not that every remote page proves a release result.
2. **Relative evidence is not frozen to the advertised source SHA.** The introduction says the relative links identify files in the pinned `6536` tree, but `../../tests/...`, `../../crates/...`, and `../../README.md` resolve relative to whatever commit hosts the matrix. At reviewed `67b386c`, these source files are unchanged from `6536`, so the current statements can be reconciled to the base. On any later update they can drift. Use `blob/6536a586...` permalinks for factual source claims or explicitly label relative paths as navigation and recheck them at each candidate. The two CI run IDs are correctly bound to `6536` and cannot support `67b386c` or a later candidate.
3. **§7 rendered-pixel reproducibility is only a procedure in G01.** The spec allows GPU pixel variation *compared with documented tolerance*. G01 asks for a tolerance and comparison procedure, but its measurable predicate only requires identical parametric/metric bytes. Add a separately observed render comparison, tolerance, environment and pass/fail result to G01 before it can pass. This does not require bit-identical PNGs.
4. **Issue #20's final release-evidence contracts lack explicit disposition rows.** G11/C06–C08 mention final CI, clean demo, licenses and review in aggregate, but do not enumerate the issue's required final **Rust format/Clippy/tests, Python lint/tests, schema, security/reliability, golden demo, artifact validation**, with exact candidate-bound commands/exits, or the **candidate/tag proposal, changelog/release note, known limitations, and each blocker/exclusion disposition in its owning GitHub issue**. Add checkable subrows or a final candidate checklist, including the README/install guide matched to the exact candidate. A successful `rust` job on `6536` covers only its Ubuntu steps: locked Cargo metadata, format, Clippy, workspace tests and schemas. Its workflow has no Python lint/test, installed Blender/IFC, native desktop, clean Omarchy or full demo job.
5. **Keep the published-head/A22 boundary explicit on refresh.** Live PR #27 head and `feat/release-0.1` are `6536a586...`; PR is draft and `REVIEW_REQUIRED`. Commit `4cfd0b82e86c1fa57fb1611eb8f844f3df586cd0` (A22 read-only project/run status) is an ancestor of `6536`, so this is already in the pinned source. The separate A22 worktree at base `15446eeaf316846936a093377041b8c1d2874092` has uncommitted desktop open/install changes and is not candidate or target evidence. Its [round-two scoped review](https://github.com/butahlecoq/Archy/blob/4cfd0b82e86c1fa57fb1611eb8f844f3df586cd0/docs/plans/omarchy-desktop-status-review-round2.md) covers development-profile read-only status, expressly not installed Omarchy behavior or launch/approval authority. No G06/C09/G11 promotion follows from A22 notes.
