## Attack surface and limits

`initialize` validates the JSON before creating `project`, opens each absolute ancestor descriptor-relative without symlinks, requires an owner-controlled private state directory, creates `project` and `project.json` exclusively, syncs their entries and file, then compares path identities. `open` and `check_owner` pin device/inode/mount identity and source digest. `BoundProjectRead::transact` checks source and root binding around the project lock and publication; core uses create-only revisions, request fingerprints, full history verification, and synced replay. The wrapper verifies the generated run again before returning a receipt. No agent-supplied actor, check, artifact path, manifest, or chain hash enters this generation call.

The tests above exercise race-adjacent replacement and tamper refusals, but they do not exhaust all initialization/commit interleavings. The source and project directory are broker-UID owned; a separate untrusted UID cannot rename inside them under the required 0700 state path. A process with broker UID or root can still rewrite or roll back protected state, and the journal has no external monotonic anchor. No privileged bind-mount race or two-UID Omarchy test ran here. The path wrapper records mount IDs, while core's managed-path traversal uses `NO_XDEV`; the mount case still needs a disposable privileged target test. File-system I/O has no wall-clock bound. The snapshot reader has 16-revision/32 MiB limits; the writer's preflight and CLI transaction still use full accepted-history scans, so a trusted large or damaged history can cost more work before refusal. I did not reproduce an agent-triggered exhaustion path through the private state directory.
