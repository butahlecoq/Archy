Status: CLI orchestration and edit workflow are implemented for independent review. Storage round1 was accepted separately in `task03-storage-review-round1.md`. This handoff does not claim full A05 acceptance or actual Omarchy execution.

## API and behavior

- `archy_cli::generate(GenerateInput)` and `archy_cli::evaluate(EvaluateInput)` are the reusable service entry points. The binary dispatches to them; later typed tools can call the library directly.
- `MutationOptions` carries an optional idempotency key, expected revision and destination. Without a key the service creates a fresh UUID and reads the current revision under lock. An explicit key requires an explicit expected revision. Core storage fingerprints the versioned request and resolves replay before stale-revision rejection.
- `verify_run(project, run_id)` returns `TrustedRun` only after full accepted-chain byte verification, operation artifact inventory checks, exact source-to-normalized correspondence, supported recorded algorithm checks, canonical generation/edit derivation, full evaluation recomputation and report/event byte recomputation. Core storage continues to return structural evidence only. The trusted view is constructed privately and cannot be supplied by stored booleans.
- Verification walks parent links iteratively with cycle detection bounded by the accepted revision count. A new read-only `LockedProject::accepted_history()` handle validates the chain once and rechecks selected run bytes against their accepted receipt, avoiding repeated whole-chain reads for each ancestor. This addition to reviewed core storage needs coordinated rereview.
- `generate --count/--seed` persists source, normalized input, generation result, variants, evaluations, reports and event log. `evaluate --variant/--all [--run]` selects an immutable generation/edit run; default selection is the latest accepted one. An implicit-source replay recovers the original parent run. Neither command substitutes later edits to the current project file into historical runs.
- `generate --from-run/--variant/--params` reads a bounded descriptor-relative project file. The strict parameter object contains only `parameters`, `storeys` and `floor_to_floor_m`. The canonical variant constructor derives ID and geometry from the selected parent seed. The edit and a later restoration each create a new run; historical artifacts remain readable.
- A successful persistence with failing required checks exits zero but reports `all_required_checks_passed: false`. An exhausted generation reports false with explicit explanations. The receipt is a persistence outcome, not design approval.

## Review targets

No task02 algorithm files or frozen doctor source were edited for this slice.

Adversarial tests cover consistently rehashed changes to metrics, checks, tolerance, parity budget, aggregate status, variant ID/footprint/project binding, normalized snapshot and report. Core structural reads accept those self-consistent hashes; the CLI verified reader rejects them. A further test changes the recorded algorithm and rehashes the revision link. Tests also cover replay after later revisions, stale and changed requests, edit/restore, source-file edits, failed checks, exhaustion, CLI usage conflicts and structured operation errors.

Gauss's final CLI review finding is addressed: evaluation fingerprints the bounded raw selector before checking whether a selected variant exists. For an accepted explicit key, the service also compares the recorded operation and parent run before attempting to load a changed source ID; edit mode compares its recorded parent run and parent variant before loading a changed parent. The original request replays its receipt, a changed absent selector or valid-but-absent parent UUID returns `REVISION_CONFLICT`, and a fresh key with that absent parent retains the normal missing-artifact error. New requests still verify the source and selected variant before publication. Binary and service regressions assert the error envelope and unchanged revision.

Gauss observed a parallel test failure with the exact retriable `REVISION_CONFLICT` message `project lock held by another process`. A parallel short-suite loop reproduced that response at another direct lock assertion; the cause of the transient lock holder was not established. The test file now retries only that exact code, field, retriable flag and message, at most eight attempts with 5 ms between attempts. All other errors return immediately; persistent contention still fails. No workspace-wide serialization or production retry was added.

Preliminary CLI review findings in `task03-cli-review-preliminary.md` are addressed in source: a 65-edit chain reaches revision 66 and remains readable; same-key changed malformed source/parameter bytes return `REVISION_CONFLICT` before parsing; mixed generate/edit/evaluate history keeps default selection on the latest generation or edit run. The deep chain test takes about 69 seconds in the debug workspace test profile. The accepted-history core accessor is intentionally narrow and has a regression proving that artifact tampering after the chain snapshot is detected on the selected read.
