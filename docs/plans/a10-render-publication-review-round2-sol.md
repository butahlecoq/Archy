## Finding: P1 — fully transparent PNGs pass the independent preview verifier

`render_verify.rs` `verify_png()` accepts RGBA images and counts RGB distance from the first pixel, but never checks alpha. An image can have varying RGB data under alpha zero and display no visible pixels. The success path calls this verifier after capture and then publishes `RenderResult::Verified` when it returns `Ok`; stored verified replay calls the same verifier. Thus the stated nonblank preview guarantee is false even though the GLB is valid.

I compiled a disposable probe using the exact frozen `render_verify.rs`, pinned `png = 0.18.1` and `gltf = 1.4.1`, the frozen fixture variant/evaluation/GLB, and three generated 512×512 RGBA PNGs whose **every alpha byte is zero**. Command (from this worktree):

```sh
TMPDIR=/home/butahlecoq/work/archy/.tools/targets/a10-render-review-r2/tmp \
CARGO_TARGET_DIR=/home/butahlecoq/work/archy/.tools/targets/a10-render-review-r2 \
CARGO_NET_OFFLINE=true RUSTUP_AUTO_INSTALL=0 \
cargo run --offline --manifest-path /home/butahlecoq/work/archy/.tools/targets/a10-render-review-r2/parser-probe/Cargo.toml
```

Output: `transparent PNG len=2201 result=Ok([("view-top.png", 261820), ("view-front.png", 261820), ("view-iso.png", 261820)])`; exit 0. Expected: `ARTIFACT_INVALID` for previews with no visible foreground. This proves the reader defect, not that an installed supervised Blender job emitted these bytes. The parser accepts the exact PNG bytes it is given; an independently hashed worker claim would not make the image visible. Require visible foreground after compositing or enforce a documented opaque-alpha profile, then test transparent and partially transparent cases through the actual success reader.

## Boundary and limit review

- **Exact bytes, claims, path:** Adapter capture reads a fixed response and five fixed Blender names using `openat2` beneath the scratch directory, refuses symlinks, hardlinks, nonregular files and unexpected entries, caps individual and aggregate sizes, and checks hashes against typed response claims. Its tests passed for extra/missing entries, traversal, claim mismatch, symlink/hardlink/FIFO, size edges, and handled error responses. `RenderResult::Verified` lists six published files including response; replay checks their bytes, metadata and claims, then reparses the stored GLB/PNGs. The fake-success adapter fixture is deliberately only byte/claim capture: it does not confer geometry authority. `scene.blend` is retained and hashed but not independently parsed, so scene-to-GLB equivalence is not proved.
- **Parser profile and geometry:** PNG input is capped at 4 MiB, decoded 512² RGB/RGBA 8-bit frames at 1 MiB, with an 8 MiB decoder allocation limit; animation is refused. GLB input is capped at 8 MiB, with external resources, required extensions, skins, animations, morph targets, non-triangles, missing default scene, depth >16, >32 solids, >100,000 aggregate vertices or >300,000 aggregate indices refused. It transforms nodes to Z-up, checks footprint containment/corners, height, bounds, oriented closed edges, roof area, signed volume, storey count/order, and GFA against the evaluated source. The real fixture decodes; corrupt/truncated/wrong-geometry/oversized cases in its unit test reject. The 8 MiB source cap is **not** a measured peak-memory cap: GLB JSON is materialized as `serde_json::Value` and parsed again by `gltf` before vertex/index count checks. No near-cap peak-memory or adversarial hole/overlap/connectedness probe was run here. Roof area and volume aggregates do not by themselves prove exact footprint coverage or a single connected solid. The transparent-PNG counterexample above is run-backed; these geometry and memory points remain proof limits, not additional confirmed bypasses.
- **Failure, source and recovery:** Render selects an accepted evaluated snapshot while holding the project lock, binds the original input digest and request selector, starts a pending run before launching workers, and writes per-variant failures separately from design checks. The observed failed run retained the evaluated source manifest byte-for-byte in the focused test and replayed idempotently. Core storage uses staged synced artifacts, no-replace rename, a revision receipt, and orphan recovery that rechecks stored bytes; storage fault tests are reported below. A captured worker error's SHA is retained in the failed record, but its response bytes are not published, so replay cannot re-audit that diagnostic response. This does not yield verified success.
- **Fixed production gate and packaging:** The CLI requires `/usr/lib/archy/archy-service-gate` at a canonical root-owned immutable path; the gate source fixes backend argv, request validation, inventory, cgroup and scratch policy, and worker exit/response agreement. The installed path and `/usr/bin/blender` are absent on this WSL2 host (`6.6.87.2-microsoft-standard-WSL2`), so fixture success and unit tests are not evidence of installed launch or teardown. Packaging uses the locked normal dependency graph of both CLI and service gate; `locked_graph()` reported 106 registry crates including exact `png 0.18.1`, `gltf 1.4.1`, `gltf-json 1.4.1`, `gltf-derive 1.4.1`, `fdeflate 0.3.7`, and `flate2 1.1.10`.
