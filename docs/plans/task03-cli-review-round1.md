# A05 CLI scoped round-one rereview

**Decision: the final-review P2 replay-ordering finding is addressed on the frozen CLI source.** This rereview covers changed evaluation selectors, changed absent evaluate/edit parents, and the new test-only retriable-lock retry in `crates/archy-cli`. It does not accept A05, the renderer/golden review, or Omarchy release behavior. I made no source edits, commits, pushes, or agent calls; this document is the only repository write.

## P2 disposition and source ordering

[`evaluate.rs:14-78`](../../crates/archy-cli/src/evaluate.rs) locates a prior explicit key, checks operation and parent binding, serializes a bounded raw selector, and calls `LockedProject::begin` before selecting or validating a variant. The existing-key request therefore reaches core fingerprint comparison before a changed nonexistent selector can return a selector error. For a changed valid-but-absent parent UUID, the recorded parent comparison returns `REVISION_CONFLICT` before any new-source load; for a fresh key, core attempts the read and returns the normal `ARTIFACT_INVALID`. After `begin` creates a pending run, the service still calls `verify_locked` and validates the source operation and variant before publication. [`generate.rs:97-144`](../../crates/archy-cli/src/generate.rs) similarly checks an accepted edit key's operation, parent run, and parent variant before reading a changed parent, while retaining parameter-byte fingerprint comparison in `begin` and prepublication trusted-parent validation. [`lib.rs:107-129`](../../crates/archy-cli/src/lib.rs) obtains recorded manifests through the validated receipt reader; it does not grant trusted design status from those manifests.

I independently ran the actual `target/debug/archy` binary against disposable courtyard-project copies. In the evaluation probe, generation committed revision 1 and an explicit-key one-variant evaluation committed revision 2. Reusing that key/revision with `--variant absent-variant` exited 1 with `REVISION_CONFLICT`, field `storage`, `retriable:false`. Reusing it with an absent UUID as `--run` produced the same conflict; a fresh key with that absent source returned `ARTIFACT_INVALID` (`run is not accepted`). Replaying the original request returned the exact original receipt, and only two revision files existed. A separate edit probe showed the same changed-absent-parent conflict, fresh-key missing-parent error, exact receipt replay, and two revision files. The committed service regression at [`core_workflow.rs:682-789`](../../crates/archy-cli/tests/core_workflow.rs) also exercises changed selector/source, binary envelopes, replay, and unchanged revision; [`core_workflow.rs:832-889`](../../crates/archy-cli/tests/core_workflow.rs) covers edit-parent and malformed replay inputs.

## Parallel lock-flake evidence

The new [`core_workflow.rs:26-66`](../../crates/archy-cli/tests/core_workflow.rs) helper retries at most eight times, sleeping 5 ms only for the exact `REVISION_CONFLICT` code, `storage` field, `retriable:true`, and `project lock held by another process` message. All other errors, including stale-revision and changed-request conflicts, return immediately; final-attempt contention is returned. The helper is confined to this test file. It does not change production locking or serialize CI tests. The author's handoff reports a pre-helper parallel short-suite reproduction at another lock assertion and 20 passing short-suite runs with the helper. I independently ran five default-parallel short-suite iterations, each with 15 passed and only the long depth test filtered, plus the full default-parallel workflow target with all 16 passed. These passes show the test remains runnable under the observed transient, **not** that the underlying lock holder or cause was identified or eliminated. The exact-error helper could absorb an intermittent contention event without reporting its frequency; no such event was measured in my runs. No stale conflict is swallowed by its match predicate.
