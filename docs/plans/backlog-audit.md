# Release 0.1 backlog coverage audit

Audit date: 29 October 2026. Compared [backlog.md](backlog.md) with the complete [release specification](../specs/release-0.1.txt), [design decisions](design-decisions.md), [first-slice brief](task-01.md), upstream README, architecture, integrations, project structure, proof-of-concept and roadmap documents. This is a document audit, not implementation verification. No backlog or implementation files were changed by this audit.

The backlog covers all D1–D20 and every named §7 acceptance gate. No entire release subsystem is omitted. D1–D2 is the first implementation slice; it cannot constitute completion of release 0.1. The following concrete gaps and ambiguities should be resolved in owning issues before closure.

## Gaps or underspecified acceptance evidence

| Priority | Source requirement | Finding | Suggested resolution and owner |
|---|---|---|---|
| Required process | §8: protected main, trunk-based small PRs | The global review rules cover PR review but no ticket explicitly configures or verifies protected main. Repository rules are outside source-file boundaries. | Add an A01/A20 repository-settings checklist: inspect/configure the permitted branch protection/ruleset, required checks and review rule; capture actual settings evidence. If account permissions prevent it, record the blocker rather than assuming protection exists. |
| Required data | §4 exact required entity fields | The backlog names shared types and individual behaviors, but does not make every entity field a schema acceptance assertion. Most vulnerable omissions are `Artifact.media_type`/`producer`, `Metric.method_version`, `Constraint.unit`/`authority`, and canonical `Site.north_angle_deg`. | Add field-level schema fixtures to A01/A02/A04/A09/A14. Assert required canonical fields and their semantics; distinguish illustrative input aliases (`project_id`, `value_m`, `north_deg`) from canonical output names. Missing legal source/authority may be explicit unknown/unverified; it must never become implied verified law. |
| Required journey | Executive decision and §2: editable alternatives with immutable snapshots | A03 promises editable parameters and immutable snapshots, but no acceptance example demonstrates editing an alternative and deriving a new reproducible iteration while preserving the original. | A05/A17 should document/test the supported parameter-edit → new run/variant path, retained parent/provenance and unchanged prior hashes. A new UI or editing command is not required; an explicit supported file-based workflow is sufficient. |
| Required ordering | §2: compute metrics/checks before rendering | A05 states rendering is downstream of evaluation, but A09's direct `render` acceptance does not explicitly enforce this ordering. | A09/A10 should test calling render on a generated but unevaluated variant: either evaluate automatically through core APIs or refuse with actionable status. Missing evaluation must never be presented as passed constraints. |
| Required brief content | §2: preferences | A02 strictly rejects unknown fields, and A14 uses preferences, but no A02 schema acceptance explicitly preserves a preference field. | Define a small bounded preference representation in A02 and carry it through snapshots/reports in A05/A14. | Delivery detail | §6 week 4: benchmark examples | Analytic fixtures and the golden demo are covered, but no ticket explicitly owns benchmark examples or records resource/runtime observations. The source specifies no performance threshold. | A18/A19 should identify the golden and analytic examples as the benchmark set and record reproducible invocation, hardware, elapsed time and artifact sizes. Do not invent a mandatory throughput target or a large benchmarking subsystem. |
| Test precision | §4.2: recorded tolerance and algorithm version | A04 chooses 1e-6 m analytic tolerance, while area/GFA and transformed artifact checks need dimensionally appropriate comparisons. A10/A13 say recorded tolerance but do not define its units. | A04/A10/A13 should state length/area/transform comparison policy and version in fixtures/reports, including how length tolerance propagates to area. Keep exact manifest reproducibility separate from numeric geometric and render-image tolerance. |

Immutable input snapshots per run, run IDs, cancellation, resource/network boundaries, draft exports, independent IFC validation, all nine MCP tools, exact stable errors, idempotency/revision checks and real Omarchy evidence are already assigned; these are not missing requirements.

## Scope and tracker status

The backlog correctly keeps the explicit §12 Month-2/Month-3/later roadmap separate: richer/courtyard forms, facades, Pareto selection, room/circulation graphs, detailed IFC semantics, validated energy/daylight/cost, CAD backends, review UI and collaboration remain future work. They do not excuse omissions from the complete release-0.1 Rust/Python, CLI, MCP, rendering, IFC, security and acceptance scope.

Local A01–A20 descriptions exist, but remote GitHub issues remain pending because authentication is unavailable. There is no evidence here of issue publication, branch protection, PR creation, CI passage or release publication. A20 must reconcile remote issue links and actual evidence before claiming the requested tracker workflow complete.

No concrete source acceptance gate was found missing from the ledger. The corrections above tighten ticket closure criteria and remove contradictory guidance; they do not reduce required release scope or certify implementation completion.
