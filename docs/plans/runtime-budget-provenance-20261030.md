## The 180-second service budget

The A09 manager sets `RuntimeMaxSec=180s`, `CPUQuota=100%`, `MemoryMax=2G`, zero swap, and `TasksMax=64`. It starts the gate before releasing the request; the gate audits the full runtime before launching the worker. The manager budget includes startup and sandbox overhead. The controller also has its own post-release 180-second wait.

Two separate disposable network-disabled Arch containers installed the existing package with `pacman -U`, then ran [`runtime_budget_probe.py`](../../tests/security/runtime_budget_probe.py). Docker enforced `cpu.max=100000 100000`, `memory.max=2147483648`, `memory.swap.max=0`, and `pids.max=64`. Each probe ran the actual installed gate and then the packaged worker as `nobody`; IFC generation, fresh reopen and EXPRESS validation passed, and Blender produced a GLB and three PNGs whose digests were checked. The probe records wall time, child CPU time, CPU cgroup counters, load average, exit status and worker output. It does not launch the production gate's full handshake or bwrap. It does not measure systemd, publication or target Omarchy.

The machine exposed eight virtual CPUs on an Intel i7-8665U WSL host. Its 1-minute load averages at probe start were 16.15 and 16.87. Cache state was uncontrolled; installing the archive preceded each measurement and Blender followed IFC in each container. The first run overlapped upstream source downloads. These are two observed direct-path samples, not a latency bound or target performance claim. A separate intact audit was still running at 107 seconds under shared load; its exact completion time was not recorded. A different negative audit hit its 120-second test limit while the gate was still running. In this container, invoking the packaged bwrap with user and PID namespaces exited 1 with `No permissions to create a new namespace`. Therefore an actual A09 systemd/cgroup/bwrap run, with an appropriately representative load and cold/warm cache, remains required to decide whether the total 180-second policy is viable. Do not increase A09's authority or timeout on the basis of these samples.

## Notice placement and source correspondence

The tested package has no `/usr/share/licenses/archy-runtime` directory. Its runtime contains Blender's `license/license.md` and license trees, Node's `LICENSE`, web-ifc's `LICENSE.md`, wheel texts and separate IfcOpenShell/bubblewrap texts. The revised staging code copies those package-specific texts to `/usr/share/licenses/archy-runtime`: all declared wheel `License-File` entries plus 15 wheel `METADATA` files, Blender's full notice tree and copyright, Node/web-ifc texts, both worker texts, and the separately sourced runtime texts. The generated PKGBUILD's license list now includes the SPDX identifiers and custom licenses enumerated by the pinned Blender notice. This follows [Arch's package license placement and metadata guidance](https://wiki.archlinux.org/title/PKGBUILD#license). A local staging check copied 50 declared wheel notice/metadata files and 35 runtime notice files; the 35 runtime copies matched their source hashes and all had mode `0644`. `makepkg --printsrcinfo` parsed the revised license array. The final package has not been built or checked for pacman ownership of these new paths.

The pinned Blender binary archive SHA-256 is `0d2b8bb2efe97e6c8eb57de6b7322f8800e1984e3125b60decca5f6771e4773e`, matching the [official 4.5.15 SHA-256 list](https://download.blender.org/release/Blender4.5/blender-4.5.15.sha256). The separately downloaded [Blender 4.5.15 source archive](https://download.blender.org/source/blender-4.5.15.tar.xz) has local SHA-256 `9c72bf73b5bf59890fd44e1320c3af308a2998db0cb330d68d5bd54cc8687e06`; its MD5 `30043bfec00c8a3eb63794a97e67544d` matches Blender's published MD5 file. The source and binary archives' `release/license/license.md` bytes both hash to `bbbae8a955a571bbd30e91c579f6f1633ec921f6317cfac9074338dfba33a7b8`. The source archive's local SHA and matching notice do not prove every native component or build input corresponds to the binary.

The pinned IfcOpenShell wheel SHA-256 `39fb69217fca787264ada575e10b46b2c038c96f85810bc5275b6b505fa91f7e` matches the [PyPI 0.9.0.post1 release record](https://pypi.org/project/ifcopenshell/0.9.0.post1/). PyPI lists no source distribution or provenance attestation for this release. The official `ifcopenshell-python-0.9.0post1` tag resolved via `git ls-remote` to commit `2744f8426bdef98a486406628a121298a5479690`; the downloaded tag archive SHA-256 is `2776eef7ddc0137df317f0294623523dc4ccdaba468c172232cfdda13f4e912a`. Of 513 wheel Python files, 495 match the tag archive directly; the sole differing common file is `__init__.py`, whose only change sets the wheel version to `0.9.0.post1`. Sixteen other files match two source submodules exactly, and the remaining `ifcopenshell_wrapper.py` identifies itself as generated by SWIG 4.2.1. These comparisons do not prove how the native files were built. The GitHub tag API request returned HTTP 403 due to rate limiting; `git ls-remote` and a separate read-only partial Git fetch succeeded.

The tag's Git tree pins `python-mvdxml` at `83c12fa494b9d6a5a370d8525dc1f76aa5c89d8d` and `step-file-parser` at `9400d243d880dace57490949d74ab1932ce99a09`. Its bundled filenames include OpenCASCADE 7.8, OpenCOLLADA, Boost, GMP, MPFR, PCRE, CGAL-related plugins, Manifold, wgpu-native and libxml2. Names and SONAMEs identify leads, not exact upstream source revisions, build options, complete copyright notices, or license conclusions. The IfcOpenShell and two submodule LGPL texts do not close those third-party components. [Upstream discussion of the CGAL plugins](https://github.com/IfcOpenShell/IfcOpenShell/discussions/9298) reinforces the need to identify the exact build and affected components; it does not identify this wheel's complete source. Before distribution, obtain and independently review exact source/build provenance and the corresponding third-party notices and source availability for the wheel's native libraries, the Blender binary dependencies and the web-ifc WASM. The present audit establishes specific gaps and a reproducible inventory; it does not establish legal compliance or binary reproducibility. A12's reviewed ae7 JS, IFC worker and fixture bytes must also be snapshotted and tested together before the final runtime package and patch are frozen.

A practical alternative if upstream cannot supply immutable build-cache evidence is a controlled disposable source build from a full IfcOpenShell commit and pinned submodules, dependency archives and patches, image digest, compiler, Python, SWIG, CMake and Rust/Cargo.lock. Preserve link maps, logs and a per-binary source/notice inventory; compare native hashes and behavior to the pinned wheel, and lock a replacement wheel under a new digest if it differs. This is a proposed path, not a completed build or license conclusion.
