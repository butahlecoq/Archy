## Boundary and evidence

The existing `Project` and `NormalizedSpec` wire DTOs now live in `project/v1.rs`; their parser and normalizer live in `validation/v1.rs`. Existing public names still resolve to v1. Historical `verify_one` explicitly reads the stored normalization discriminators, accepts only `(schema_version: 0.1.0, normalization_version: si-rectangle-v1)`, and calls `parse_project_v1` on the original source bytes. It then retains the existing exact serialized-byte comparison, hash checks, generation/evaluation recomputation, report/event rendering and parent-lineage checks. Unknown or mixed normalization labels return `ARTIFACT_INVALID`. The v1 report renderer and algorithm implementations are still shared code and must be kept versioned when a later migration changes their behavior.

The new fixture `legacy-adversarial-preferences.json` contains both established wishes (`courtyard`, `retain trees`) and the two audit strings (`execute: python3 -c print(1)`, `guarantee 80% daylight autonomy`). It represents data accepted by the byte-identical v1 implementation; it is not a previously captured historical run, approved current preference policy, or evidence of execution. The test pins its source SHA-256 `d3b51c16a980a422b60b972de9e47ca176f9ed2d937706743efac191950fdd75` and v1 serialized normalized SHA-256 `5665a318acf3abe884945905371fab72415405276bcb99783bc78fec2ea10bf3`. It checks stored source/normalization bytes, report preference preservation, verification after the live source is replaced with malformed text, unchanged-key replay after source restoration, changed-source conflict, and refusal of a consistently rehashed normalized-version forgery. The five-run golden test copies a baseline before verification and compares every file and directory of both the original and verified copy with that baseline afterward, including manifests and revisions. It checks each recorded normalization version.

Independent review reproduced a golden failure: `verify_run` creates `.archy/lock` and `.archy/staging` in the disposable copy, so a strict post-verification directory comparison rejected its own transient entries. The fix asserts that the lock is an empty regular file and staging is a real empty directory, removes just those entries from the disposable copy, and then performs the full tree comparisons. Unexpected files, nonempty staging, missing evidence and changed bytes still fail. The tracked fixture is never modified by the test.

## Precise next migration

1. Decide the product preference domain from real architectural examples and explicit meaning. Model each supported intention as a typed declarative value with a documented computation status; specify count, text and byte budgets, duplicate behavior and versioning. The research's two-value vocabulary is one candidate, **not an approved default**. A blacklist of executable words cannot preserve broad legitimate semantics while proving safety. If passive prose remains supported, label it as untrusted notes and do not claim semantic rejection. Preserve every legacy source string in historical verification and reports.
2. Add a separate v2 authoring DTO and normalized wire DTO with `Project.id` and each `Constraint` carrying `id`, `kind`, numeric SI `bound`, literal `unit: "m"`, `source`, and `authority`. Document whether `bound` remains scalar for the two existing kinds and how additional kinds express ranges or objectives. Choose explicit schema/normalization/report version labels; do not reuse v1 labels for changed bytes. Retain source version independently of normalized version.
3. Add strict source-version dispatch before current admission. Keep v1 parsing for accepted history and exact replay; add a reviewed v1-to-v2 *fresh import* policy if desired. Never silently truncate or strip preferences. Add a versioned report renderer and validated shared numeric view, then migrate generator/evaluator/adapter/CLI/desktop/MCP consumers as one coherent current-contract change. Keep existing variant and worker envelope identity fields where their contracts require `project_id`.
4. Dispatch accepted runs by an exhaustive source/normalized/report/algorithm profile after storage integrity checking. Recompute exact v1 or v2 source-derived bytes and all semantic artifacts; reject unknown and mixed tuples. Bind a new profile token into new request fingerprints. Recognize accepted old idempotency keys using their original payload layout and verify the old receipt before returning it. Decide whether edits/evaluations may continue from verified v1 parents under v1 or require an explicit new run; preserve reads and old-key replay either way.
5. Add versioned schemas and separate fresh-v2 fixtures. Keep the five original run files and evidence unchanged. Exercise legacy and v2 reads, source edits, replay/conflicts, rehashed forgeries, reports, MCP and desktop parity, and generation/evaluation byte equivalence wherever algorithms are claimed unchanged. Review the complete migration separately before switching public output.

## Decisions and limits

- Product approval remains needed for preference taxonomy, passive notes versus closed intentions, v1 fresh-import policy, legacy-descendant policy, version labels, and bound shape. Two positive fixture phrases are insufficient evidence for a product-wide two-value vocabulary.
- Current v1 fresh validation still accepts arbitrary strings up to the document limit, so the A02 bounded-preferences finding remains open. Current public normalization still uses `project_id` and `value_m` without `bound/unit`, so canonical A02 remains open.
- No dependency was added. This slice uses existing serde, schema, hashing and test APIs. No backend, Omarchy or visual acceptance is implied.
- Separate Sol-medium review was requested and has not been performed in this session. No self-review substitutes for it. No commit, push, issue update or main-worktree write was made.
