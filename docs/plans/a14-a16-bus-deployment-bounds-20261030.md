# A14/A16 deployment bounds candidate for independent review

30 October 2026. Isolated candidate: `.worktrees/a14-a16-bus-confirm-20261030-unique`. This is an unstaged, fail-closed review endpoint. `Confirm` and both seqpacket decision routes still deny. This document records the follow-on to the independent bounds review; `a14-a16-bus-bounds-source.sha256` remains the original 17-file input freeze, and `a14-a16-bus-deployment-bounds-source.sha256` is the new 17-file candidate freeze.

## Changes

- The `HumanBus` interface uses zbus's supported `spawn = false` macro setting. Its `Review` and `Confirm` handlers are now dispatched serially on the connection task, before application decoding and slot acquisition. This removes unbounded per-method task creation for **this interface**. The four-slot guard remains and is owned by snapshot work, including after client timeout. `max_queued(4)` remains a queue bound, not a byte bound. zbus's other built-in interfaces and its connection internals have not been proven to have a hard task bound.
- `Review` applies one three-second deadline from admission through peer lookup and snapshot result. Protected store read and snapshot recomputation run in a named thread with at most four concurrent workers. A timed-out worker holds its slot until it actually exits, so cancellation cannot start unlimited replacement disk work. The service returns a denial at deadline. A blocked or CPU-stalled worker is **not** killed; four stuck workers can deny future reviews until restart. This is bounded concurrent work and response time, not a hard execution-time or CPU limit. Existing byte/history limits on the protected reader still apply.
- The real private-bus fixture starts a disposable `dbus-daemon` from a test-only config with a 65,536-byte per-message limit and 262,144-byte incoming/outgoing queue limits. Eight simultaneous 1 MiB `Review` calls must fail at transport rather than return a service `MethodError`; mock logind lookup count remains unchanged and a subsequent accepted proposal produces the exact protected snapshot/digest. The same fixture still checks real unique bus names and ProcessFD credentials, active/local/seated session properties, wrong UID, denied `Confirm`, and valid review. The mock session proves code behavior, not native logind identity.

## Primary mechanism evidence

- [zbus 5.19.0 `ReadHalf::receive_message`](https://docs.rs/zbus/5.19.0/src/zbus/connection/socket/mod.rs.html) computes `total_len` from the primary header and resizes the message buffer to it. Its internal ceiling is 128 MiB. `Builder::max_queued` sets the main message queue count; it does not change this resize. The public `ReadHalf` override cannot preserve ordinary authentication and reconstruct a `Message` through public API (`Message::from_raw_parts` is crate-private). Thus stock zbus 5.19.0 cannot set an exact smaller per-connection pre-allocation receive bound through the builder.
- [zbus object server dispatch](https://docs.rs/zbus/5.19.0/src/zbus/object_server/mod.rs.html) spawns method tasks when an interface requests it. The [interface trait](https://docs.rs/zbus/5.19.0/zbus/object_server/trait.Interface.html) and macro support `spawn_tasks_for_methods = false`; the candidate uses that supported switch for `HumanBus`.
- [dbus-daemon configuration](https://dbus.freedesktop.org/doc/dbus-daemon.1.html) defines `max_message_size`, `max_incoming_bytes` and `max_outgoing_bytes` as bus-wide limits. The latter two can each overshoot by up to one maximum message. A service-specific limit therefore requires a dedicated broker boundary; changing the shared system-bus limit is an unreviewed system change and is not part of this candidate. [dbus-broker's `--max-bytes`](https://github.com/bus1/dbus-broker/blob/main/docs/dbus-broker.rst) is a per-user broker allocation limit, not a per-message service receive limit. [systemd `MemoryMax=`](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html) can contain a service cgroup but is not a per-message pre-allocation guard.

## Deployment gate and concrete next solution

The tested 65,536-byte bound exists only on the disposable private bus. The binary still connects to the shared system bus with stock zbus, where its receive path can allocate up to 128 MiB per message. **Do not stage or activate it and do not enable `Confirm`.** The private-bus test is a concrete transport proof, not an installed policy or native identity proof.

Two production paths are feasible. Preferred: upstream a zbus `Builder::max_message_size`/reader option that is enforced from the 16-byte primary header **before** buffer resize and before further reads, with a real-bus test that sends a header advertising a larger body and verifies immediate rejection without that allocation. It must preserve Unix FD authentication and zbus's existing message ceiling. The service can then keep its system-bus connection and genuine logind calls. Alternative: run a dedicated, access-controlled D-Bus broker with the tested message and queue limits, use it exclusively for the human endpoint, and query real logind over a separate system-bus connection; prove actual caller credentials, unique-name lifetime, native active local session semantics, and policy ownership on a disposable target. Neither solution is implemented as a production deployment here.

Independent review should also verify that `spawn = false` prevents a burst of method tasks in this zbus version, that a hung protected snapshot cannot escape the four-worker cap, and that the endpoint's full-path deadline is maintained under real disk stalls. The fixture uses mock logind and does not test privileged bind-mount replacement, native multi-UID policy, bus restarts, resource pressure on a target host, or package notices. Those gates remain open.
