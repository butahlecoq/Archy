## Findings

1. **P1 — A destination-parent symlink swap escapes the disposable stage root.** [`packaging/arch/package.py:61-95`](../../packaging/arch/package.py) checks destination parents during preflight, then later creates directories and opens each target by absolute/pathname. `O_NOFOLLOW` protects only the final file component; it does not prevent following a newly inserted symlink in `target.parent`. I reproduced this without modifying product source: a disposable test hook replaced the newly created `dest/usr/bin` directory with a symlink to a separate `outside` directory immediately after `Path.mkdir` returned. `stage` exited successfully, printed an inventory claiming `usr/bin/archy`, and created `outside/archy`. This requires a concurrent or otherwise controlled parent substitution; a static symlink is rejected by existing tests. It violates the slice's owned-path confinement and makes rollback path-based too. Hold and verify directory descriptors during creation/open/unlink (or use an equivalent no-symlink descriptor-relative method), and add a race/substitution regression proving no outside file and unchanged sentinels. Do not treat final-component `O_NOFOLLOW` as covering parents.

2. **P2 — Recipe preflight accepts ambiguous or non-file mandatory archive entries.** [`packaging/arch/package.py:112-133`](../../packaging/arch/package.py) rejects links/special members and unsafe names, but does not require unique member paths or verify that `Cargo.lock`, `packaging/arch/files.txt`, and `package.py` are regular files. I created two SHA-256-correct disposable tarballs: one contained `Cargo.lock` twice with different bytes; the other contained a directory named `Cargo.lock`. Both `recipe` calls exited 0 and wrote a PKGBUILD. Duplicate entries can change the extracted effective source according to extractor order, while a directory passes the claimed locked-source prerequisite and fails later at build time. Reject duplicate normalized paths and file/directory prefix collisions, require exactly one regular file for each mandatory source, and test these cases before emitting a pinned recipe. The generated `sha256sums` does pin the archive bytes; this finding concerns the pre-extraction identity/shape claim, not a checksum bypass. The [Arch PKGBUILD manual](https://man.archlinux.org/man/PKGBUILD.5.en) confirms source archive extraction and checksum handling, but no exact Arch artifact was built in this review.

## Confirmed behavior and evidence limits

- The allowlist contains 17 intended paths under `usr/bin`, `usr/share/archy`, and `usr/share/licenses/archy`; no install/uninstall hook, worker, venv, home path, project path, or service is authored in this slice. Static traversal, source/destination link, special-source, duplicate-destination, occupied-target and mode checks are present. File creation uses `O_EXCL`, inventories record SHA-256 and mode, and the normal rollback branch removes newly created files. The existing rollback test triggers an inventory-output collision **after all files were copied**, and confirms their removal and preservation of unrelated data. It does not exercise a mid-copy failure or parent substitution during rollback; add those cases when fixing P1. Empty newly created directories can remain after rollback; the brief requires prior/unrelated files preserved, not an exact directory-tree rollback.
- The synthetic recipe uses one local archive and a non-`SKIP` SHA-256, disables rustup auto-install, and builds Cargo offline/locked. The caller supplies `source-id` and archive digest; the generator verifies the digest but does not authenticate the human label against a Git revision. The handoff correctly says no source snapshot or release PKGBUILD exists. A frozen source archive, independently recorded identity/hash, reviewed offline Cargo inputs, and an actual Arch `makepkg`/`namcap`/package inspection remain future gates. The coordinator's verified Arch developer image (`sha256:c4050a4bcd4c1f640d8c77b9635bfa70f448da232f1e4b878ce2258c3998de05`) was not used for a package build here.
- Candidate `glibc` and `gcc-libs` declarations come from WSL `readelf` on a debug binary, not an Arch release artifact. The handoff labels that limitation and does not claim ABI compatibility. Its 89 registry packages and license expressions come from offline Cargo metadata; they are a candidate notice inventory, not proof of linked code or complete notice obligations. Four cached crates lack a top-level license text by the author's scan, and third-party notice texts are not staged. `license=('MIT')` and the staged Archy MIT file do not relicense those dependencies. This is a distribution gate, not a new claim of approved notices.
- The owned-path removal test unlinks only its three synthetic package files and leaves project/run/approval/config/backup sentinels. It is a useful simulation, not `pacman -R` evidence; actual install/upgrade/removal preservation remains deferred.
