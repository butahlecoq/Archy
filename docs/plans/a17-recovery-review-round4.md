# A17 staged recovery: independent round-four security and behavior review

**Verdict: PASS for the scoped staged-writer recovery and test-harness lifecycle.** I found no reproducible regression in the five requested areas. This does not close A17 or establish release acceptance.

I reviewed base `57ba4f3b55d093da340adc5b4e05558efa3cc315` with the current untracked recovery test and documents. I read the author handoff, rounds one through three, the complete `recovery_staging.rs` test, the relevant `ProjectStore` staging/replay implementation, and `docs/recovery.md`. Round three was preserved; this is an additional independent review. No product source, commit, or push was changed.

## Findings by boundary

| Boundary | Independent result |
| --- | --- |
| Writer after test-parent SIGKILL | **PASS.** The parent creates a socket pair before spawn and gives the writer one endpoint. The writer starts a reader thread; EOF after parent death exits the writer. My separate process probe killed `parent_for_sigkill_probe` with SIGKILL after `probe-ready`, waited for its writer to disappear or become a zombie within five seconds, and confirmed revision 1 and staged `unaccepted` bytes remained. Output: `parent_exit=-9 writer_stopped=True revision_1=True staged_bytes=unaccepted`. A zombie is stopped, not reaped by this test. |
| Bounded lifecycle | **PASS for exercised paths.** `wait_for_staging` has a ten-second readiness deadline; the writer's socket read has a 30-second timeout; the focused test exercises a 100 ms timeout with the peer held open. On parent panic, `Writer::drop` kills and waits before `Fixture::drop` removes the owned directory. The fresh-target suite passed both forced missing-file unwind cases and the parent-kill case. A killed outermost runner cannot run its fixture destructor; the surviving probe owns and removes its disposable root. No guarantee is made for filesystem stalls or failed OS cleanup calls. |
| Unrelated project path | **PASS for the tested authority boundary.** The helper takes its project root from the opened directory on stdin, not `ARCHY_RECOVERY_CHILD_ROOT`. With that variable pointing to a disposable unrelated project and stdin set to `/dev/null`, my direct invocation exited 0, left only `project.json`, and preserved its bytes. The suite also checks a real writer with a valid fixture descriptor while the unrelated path is present in the environment. A caller deliberately passing a directory descriptor grants access to that directory; this is outside the environment-path claim. |
| Staged-writer recovery | **PASS for one staged boundary.** `PendingRun::write` synchronizes the staged artifact before `child-ready`. The parent reads `unaccepted`, kills and waits for signal 9, reopens `ProjectStore`, observes revision 1 and refusal to read the staged run as accepted. Same-request retry commits revision 2; replay returns the exact receipt, revision remains 2, and history contains exactly the first and second receipts. The accepted data, manifest and revision-1 hashes match before kill, after reopen and after retry; the abandoned staging directory still contains `unaccepted`. The retry artifact is `after-restart`, so this proves request identity and publication behavior, not equal generated bytes. The separate focused storage replay/conflict test passed. |
| Claims and limits | **PASS.** The handoff and recovery instructions distinguish staged runs from published orphans and say the evidence covers Linux process interruption. They do not claim power-loss durability, target filesystem proof, backend cancellation/log retention, MCP single-apply, or full A17 acceptance. The parent socket is test-harness supervision, not product worker supervision. |

## Commands and observations

All Cargo commands used the new target `/tmp/archy-a17-round4-target-20261029` with `RUSTUP_AUTO_INSTALL=0 CARGO_NET_OFFLINE=true CARGO_BUILD_JOBS=2`:

```sh
cargo test --locked --offline -p archy-core --test recovery_staging -- --nocapture
cargo test --locked --offline -p archy-core --test storage commit_replay_and_conflict_preserve_prior_bytes
rustfmt --check --edition 2024 crates/archy-core/tests/recovery_staging.rs
```

Results: recovery **8 passed, 0 failed**; storage **1 passed, 0 failed**; rustfmt exit 0. The recovery run printed `Some(9)` for the staged child and revision `2` on retry. Its accepted SHA-256 inventory was unchanged before and after kill: `data` `070c160a6299c5438070b1aa737b14fc2992ed49579c14264884886a5876f971`, `manifest.json` `de07a1fe735bc28cd7e67ce7232910305472e5f9ccf42b18c03bb2cf22e48081`, revision 1 `119cd3bfc91b191a158ccbf4f1653beea187c6c57d5b2589a0dbe4552159d174`. Random run IDs change the last two hashes across invocations. The two visible missing-file panics were expected and caught by the unwind test.

The separate parent-kill probe opened a disposable directory as the test parent's stdin, passed a Unix socket as stdout, waited for `probe-ready`, recorded its writer PID and staged bytes, then sent SIGKILL to the test parent. It asserted that the writer was absent or a zombie within five seconds and that revision 1 and staged bytes remained. Its `finally` block killed the isolated process group if needed and the temporary directory context removed the probe root. The separate path probe invoked `child_stages_until_killed` with null stdin and `ARCHY_RECOVERY_CHILD_ROOT` set to a disposable unrelated project; output was `helper_exit=0 unrelated_files=[project.json] unrelated_bytes=unchanged`.
