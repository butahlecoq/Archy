## Reproduced findings

1. **High: a configured root or source can be replaced after the second binding check while a mutation is active, yet MCP reports success.** `BoundProjectRead::transact` checks the configured root and source before and after `ProjectStore::lock`, then calls generation and verifies the committed run without another binding check (`crates/archy-cli/src/project_read.rs`). Descriptor based storage prevents writing into an attacker supplied replacement root, but a successful receipt can name a path under the *configured* root where the run does not exist. Reproducer, using the built `archy-mcp` over actual JSON lines: start with `examples/courtyard-housing/project.yaml` copied to a temporary `bound/project.yaml`; send `generate_variants` with `{project_id:"courtyard-demo",count:100,seed:"42",idempotency_key:"race-1",expected_project_revision:"0",destination:"runs"}`; watch `bound/.archy/staging` for a UUID directory; immediately rename `bound` to `moved`, recreate `bound` and copy the same source there. Observed `staged_before_swap=true`, response `ok=true`, revision `1`, one revision in `moved/.archy/revisions`, and no `.archy` at the configured `bound` root. The returned `runs/<run-id>` was consequently absent beneath the configured root. A parallel probe replaced `project.yaml` with one declaring `alternate-demo` after staging appeared; MCP returned `ok=true` and `project_id:"courtyard-demo"` at revision `1` while the configured source declared `alternate-demo`. These were two successful single-shot probes, not an exhaustive timing sweep. The in-process mutation mutex and cross-process storage lock serialize cooperating transactions but do not exclude an external filesystem rename or source replacement. A late identity check alone can detect some races but cannot roll back an already published revision; the repair must define what success means under path replacement and preserve an honest receipt or refuse before publication through a defensible mechanism. No write to the replacement root was observed.

2. **Medium: an invalid evaluation selector leaves a new staging directory despite an error response.** On a fresh temporary project, a successful MCP generation created revision `1`. A subsequent `evaluate_variant` call with that accepted `source_run`, `variant_id:"variant-absent"`, `idempotency_key:"bad-selector"`, `expected_project_revision:"1"`, and `destination:"runs"` returned `INVALID_SCHEMA`. The accepted revision and run counts stayed `1`, but `.archy/staging` acquired one UUID directory. `evaluate_locked` calls `locked.begin` before verifying that the selected variant exists; `begin` creates the staging directory. Sequential invalid requests can accumulate staging directories despite the four-call concurrency cap. Validate the selector against the verified source before `begin`, or provide explicit cleanup for a pending run that was never published, without weakening crash evidence retention. Retest that failed calls leave accepted state and managed staging unchanged. A wrong or absent source also obtains the storage lock after history preflight, so a genesis error can create `.archy` scaffolding; distinguish that expected lock setup from the avoidable selector residue when specifying the failure contract.
