# ADR 0006: Canonical project and preference contract

Status: implementation candidate for separate review, 29 October 2026. The release remains 0.1; `0.2.0` identifies the changed project wire contract.

Release specification §4 requires `Project.id` and each normalized constraint's `id`, `kind`, `bound`, `unit`, `source`, and `authority`. Historical `0.1.0` runs instead store `project_id`, `value_m`, and arbitrary preference strings. Their original and normalized bytes participate in receipts, variant derivation, reports, and semantic verification.

Fresh `0.2.0` authoring uses `id` and `bound` with an explicit unit. Normalization converts the two supported constraint kinds to SI and emits `unit: m`, `schema_version: 0.2.0`, and `normalization_version: si-rectangle-v2`. The kind defines the inequality: `max_height` is an upper bound; `min_edge_setback` is a lower bound. Source and authority remain declarations, not verified law. Missing authority in a fresh `0.1.0` import becomes `assumption` as before. The v1 numeric view remains internal to unchanged generator/evaluator/worker envelopes; their `project_id` references are not renamed.

Canonical `preferences` is an ordered list of at most eight distinct `{kind, value}` intentions. Kinds are `massing_character`, `landscape_intent`, and the general `architectural_intent`. The value is 1–256 characters and at most 512 UTF-8 bytes, with no controls or shell/markup delimiters. All preferences are uncomputed and have no effect on generation, evaluation, or approval. Exact legacy strings `courtyard` and `retain trees` retain their original kinds; other declarative v1 wishes import as `architectural_intent` with their exact text and order. Unsupported legacy text fails at its index. Ordinary wishes stay preferences; `notes` remains separate passive source text with four entries, 512 UTF-8 bytes each and 1024 bytes total. Accepted v1 history bypasses fresh import rules and keeps its exact bytes.

Fresh authoring and fresh v1 imports apply the same bounded preference admission rule before building a canonical wish. In addition to the length and character limits, the runtime rejects case-insensitive whole ASCII tokens `rm`, `sudo`, `chmod`, `chown`, `curl`, and `wget` anywhere; `run`, `execute`, `exec`, `launch`, or `invoke` followed within three tokens by `rm`, `sudo`, `bash`, `zsh`, `powershell`, `cmd`, `python`, `python3`, `node`, `npm`, `npx`, `curl`, `wget`, `chmod`, `chown`, `sh`, `shell`, or `script`, skipping articles `a`, `an`, `the`, `this`, `that`; and `delete` or `erase` followed by `file`, `files`, `directory`, or `directories` under the same rule. It also rejects `run`, `execute`, `exec`, `launch`, `invoke`, `delete`, or `erase` at the start of a value unless the next token is `of`, or immediately after `please`, or after `could you`, `would you`, or `can you`. Tokens are separated by non-ASCII-alphanumeric characters, so case, quoting, punctuation and common separators do not hide these forms. The existing `execute:`, `python3 -c`, `guarantee`, and digit plus named performance-domain checks also apply. A value such as `long run of glazing` is accepted. This finite syntax rule does not infer the meaning of arbitrary prose or claim to detect every prompt injection. The enforceable authority boundary is structural: a preference has only an architectural kind and passive value, never an executable command variant, and no preference is dispatched to an agent or process. Consumers must continue treating imported text as untrusted data.

The current JSON Schema encodes local identifier, positive-number, count, shape, preference, and character-length limits. JSON Schema cannot faithfully express UTF-8 byte limits, aggregate note bytes, arithmetic overflow after unit conversion, unique constraint IDs, or the full rectangle and cross-field feasibility rules. It also cannot identify semantic performance claims without duplicating a fallible language policy. The runtime rejects these; negative parity probes document the gap. Schema consumers must call `archy validate` for semantic acceptance. YAML and JSON source parse to the same canonical model; duplicate mapping keys are rejected before normalization.

Accepted v1 runs retain their original source, normalized, report, variant, metric, event, and revision bytes. Verification dispatches only the explicit v1 or v2 normalized profile and recomputes source-derived canonical bytes and all downstream artifacts. V1 parent evaluate/edit and old-key replay keep their recorded profile. Fresh generation, including exact legacy import, publishes v2. New request fingerprints carry the v2 profile token; old accepted keys replay with the v1 request layout. Versioned v1 schemas remain under `schemas/archive/v1/` and current schemas describe v2. No dependency was added; the existing Serde, schemars, storage, and hashing stack covers the contract.

Fresh native v2 and imported v1 sources use canonical v2 normalization and authority v2 evaluation, even when no constraint claims regulation. A claimed source retains its geometric check and adds a separate required authority UNKNOWN with null measurement and limit; it cannot imply approval. Edit and evaluate inherit the verified source profile. Each new v2 run inventories `profile.json`, which fixes the accepted source schema, normalized schema, normalization version, operation, operation algorithm, evaluation version, and report version as one tuple. Verification checks that tuple against the source, manifest, evaluation, report, input and normalized bytes, and parent ancestry. Historical accepted v1 marker chains retain their original v1 evaluator and exact report bytes without a profile artifact. A rehashed v2 evaluation or normalized-profile downgrade is rejected when its source bytes remain v2; a complete locally rewritten source and chain cannot be ruled out without an external trust anchor. This decision does not assert regulatory compliance, backend execution, or a complete ontology. Historical arbitrary prose is read only as data.
