# Local MCP facade

`archy-mcp --project /trusted/path/project.yaml` starts a stdio MCP server. The launch operator supplies the fixed manifest path; tool arguments cannot choose a file or root. The server pins the project source and root descriptor at startup. Reads use the same noncreating accepted-history and semantic verification service as desktop status. A missing `.archy` history is revision `0`; corrupt managed history returns an Archy error without repair.

The server supports protocol versions `2026-07-28` and `2025-11-25`. The Rust SDK owns protocol dispatch and lifecycle. A bounded adapter screens complete lines for JSON syntax and serializes parse errors with SDK output. Incoming lines are capped at 1 MiB, JSON depth at 64, responses at 1 MiB, concurrent tool calls at four, and variant pages at 100. Mutations also use an in-process mutex and the shared storage lock. Large unsigned revisions are decimal strings at this boundary.

Project, run, and variant IDs, idempotency keys, and cursors use ASCII. Accepted run IDs are UUIDs; accepted variant IDs contain an ASCII hash. Presets, objectives, destinations, and reasons may contain Unicode. Their existing UTF-8 byte ceilings remain 128, 128, 512, and 4096 bytes, respectively. To express these ceilings in standard JSON Schema, the server also limits the number of characters to the byte ceiling divided by the widest UTF-8 character in the string. This conservative rule can reject a mixed string even when its actual byte length is below the ceiling. The input schemas and wire handler apply the same rule.

Unicode text must contain valid Unicode scalar values. An escaped UTF-16 surrogate pair for a supplementary character is accepted; an unpaired surrogate is rejected by the advertised schema. A bounded input adapter returns JSON-RPC error `-32700` with an explicit null ID for an unparseable complete line, including malformed UTF-8 or an unpaired surrogate. It does not include the input in the response. A following valid line is processed by the pinned rmcp SDK. Oversized lines are discarded, nesting beyond 64 closes the stream, and an unterminated line at EOF is discarded.

[JSON-RPC 2.0](https://www.jsonrpc.org/specification#error_object) requires a null ID when a parse error prevents detecting an ID. The error-response descriptions for both [MCP 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic#error-responses) and [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic#error-responses) instead describe an optional string or number ID. Parse errors use the explicit JSON-RPC null as required by this facade; a strict client applying the MCP type literally may reject that response. Other SDK error serialization is unchanged.

`get_project`, `validate_project`, `list_variants`, and `compare_variants` are live reads. Their successful results have `structuredContent: {ok:true,data:...,error:null}` and equivalent JSON text content. Failed reads return `isError:true` with the unchanged Archy error shape in `{ok:false,data:null,error:...}`. The output schemas require exactly one of those two states. Historical revisions starting at `1` come from verified accepted runs. An explicit revision `0` returns the pinned current source only while no accepted revision exists. Once a run is accepted, revision `0` returns `REVISION_CONFLICT` because storage has no immutable genesis source snapshot. An omitted revision continues to return the pinned current source. `get_project` and `validate_project` also recompute the accepted head ancestry before returning data. Cursors bind the configured root, project, source digest, accepted head, revision, source-run filter, and last emitted variant ID. A new accepted revision makes an old cursor return `REVISION_CONFLICT`.

`compare_variants` accepts explicit accepted generation/edit run IDs and the sole implemented objective, `absolute_target_gfa_delta`. Each returned comparison is the CLI's typed document for one run, with ranks **within that run**. It preserves source and evidence hashes, required-check results, subjective preferences, and uncomputed daylight/cost caveats. It does not claim a ranking across different runs. Pages default to one run and bind the cursor to the fixed project, source bytes, accepted revision/head, objective and ordered IDs. It neither persists a report nor acquires a writer lock. Unsupported objectives, duplicate/unaccepted IDs and non-generation/edit runs return typed errors. A comparison that exceeds the MCP response bound returns a bounded error.

`generate_variants`, `evaluate_variant`, and `render_variant` are live mutations through the CLI's locked transaction service. Each requires an idempotency key, decimal expected revision, and project-relative destination. Exact same-key retry replays a verified receipt; a changed request or stale revision returns `REVISION_CONFLICT`. Evaluation accepts only a verified generation or edit source run and validates the selected variant before creating staging for a new key. The server checks the pinned root and source binding at entry, after locking, at publication boundaries, and after verifying the accepted run. A detected binding change before the staged run rename refuses publication. A detected change after run publication returns a retriable `REVISION_CONFLICT` with an uncertain outcome; retry the same key after restoring the binding to discover or recover the receipt. Storage writes use the pinned root descriptor and cannot be redirected to a replacement root.

The binding checks do not lease the configured pathname. An uncooperative rename between a check and publication or response can escape detection. A success receipt describes the pinned project and the checks that were observed; it does not guarantee that the configured pathname continuously identified that project. The returned path is project-relative and may be unavailable under a replaced configured path. Do not infer atomic pathname identity from a successful response.

`render_variant` requires an explicit accepted evaluation run, one variant ID, and the fixed `draft` preset. It returns a typed immutable receipt with `all_verified` and each variant's `verified` or `failed` status. A worker failure is retained as a failed variant in a successful transaction envelope with `all_verified:false`; a verified artifact result is returned only after bounded capture and independent verification. The worker is launched through the fixed installed service gate. If that gate is absent, the result is a replayable `failed/BACKEND_UNAVAILABLE` receipt with no preview or GLB success claim. This source integration remains provisional until A10's separate review and installed Omarchy gate pass.

All nine planned tools have strict advertised input and output schemas in [`schemas/mcp`](../../schemas/mcp). `export_ifc` and `propose_approval` return typed `BACKEND_UNAVAILABLE` prerequisite errors. There is no final approval, generic filesystem, shell, network listener, or client-selectable root tool. Tool failures use `isError:true` and structured envelopes, consistent with the [official MCP tool contract](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) and [Rust SDK](https://github.com/modelcontextprotocol/rust-sdk).

Run the wire checks with `cargo build --locked -p archy-mcp -p archy-cli`, followed by `python3 crates/archy-mcp/tests/stdio_contract.py`, `python3 crates/archy-mcp/tests/parse_errors.py`, `python3 crates/archy-mcp/tests/compare_stdio.py`, `python3 crates/archy-mcp/tests/mutations.py`, and `python3 crates/archy-mcp/tests/render_variant.py`. All five scripts honor `CARGO_TARGET_DIR` and run from the CI schema checker. `cargo test --locked -p archy-mcp` tests transport guards and writer backpressure. If Node.js is available, `node crates/archy-mcp/tests/unicode_regex.js` also checks the patterns in an ECMAScript UTF-16 regex engine.
